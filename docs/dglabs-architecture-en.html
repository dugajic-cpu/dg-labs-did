Technical Architecture

KYC Identity Onboarding Pipeline

A production-grade serverless pipeline combining email OTP verification, biometric passport verification, Microsoft Entra Verified ID credential issuance, and cryptographic presentation. Built on Azure, deployed and tested with real external users.

Pipeline Flow

Nine steps from email to verified credential

Each step is a discrete serverless function. The pipeline is event-driven — no components are running or costing money between invocations.

1
Email verification — OTP
Applicant visits onboard.html, enters email and completes reCAPTCHA v2. send-otp validates the reCAPTCHA server-side with Google's API, enforces a rate limit of 3 requests per 10 minutes per email, generates a 6-digit OTP, stores it in Azure Table Storage with a 10-minute expiry, and sends it via Microsoft Graph API. verify-otp checks the code and deletes it on success — preventing replay attacks.
send-otp verify-otp Azure Table Storage Microsoft Graph API Google reCAPTCHA v2
2
Request submission & enrichment
After OTP verification, applicant submits their name and passport country. submit-request extracts IP address from x-forwarded-for headers, parses browser/OS/device type from the user-agent string, calls ipwho.is for geo enrichment (city, region, ISP, timezone), and stores all fields in Table Storage. Sends admin notification email with full context via Microsoft Graph.
submit-request Azure Table Storage Microsoft Graph API ipwho.is (geo API)
3
Admin review & approval
Administrator logs into admin.html protected by Microsoft Entra MFA. After Microsoft login, a function key gate provides a second authentication layer. The admin panel displays all requests with IP, geo, and device data. On approval, approve-request creates a Veriff verification session with the applicant's email in vendorData, emails the Veriff link to the applicant, and updates Table Storage status to veriff_sent.
approve-request list-requests Azure Static Web Apps (auth) Microsoft Entra ID MFA Veriff API Azure Table Storage
4
Biometric verification — Veriff
Applicant receives the Veriff link by email (valid 7 days) and completes passport + selfie verification on their phone. Veriff's Full Auto AI engine evaluates the submission — typically within seconds. No human review required. The email is stored in vendorData to link the Veriff session back to the DG Labs request record.
Veriff Essential — Full Auto AI Biometric passport + liveness FINMA-aligned assurance level
5
Veriff webhook — vc-onboard
On approval, Veriff fires a fullauto webhook POST to vc-onboard. The function parses the payload (handling both test and live fullauto formats), extracts the applicant's email from vendorData, and builds a personalised claim.html URL containing email, firstName, and lastName as URL parameters. Sends the "Credential is ready" email with a permanent claim link via Microsoft Graph.
vc-onboard Veriff fullauto webhook Microsoft Graph API
6
Credential issuance — proxy + Entra Verified ID
Applicant clicks the claim link, which opens claim.html and immediately calls vc-issue-proxy. The proxy validates input, checks Table Storage — if status is credential_issued and more than 15 minutes have elapsed, it returns 403 (blocked). Otherwise it calls vc-issue internally with the function key stored in Azure environment variables (never exposed to the browser). vc-issue authenticates with Microsoft's Verified ID API using client credentials flow (scope: 3db474b9-.../.default), builds the issuance request with authority, manifest, type, and claims, and returns a QR code (base64 PNG) and openid-vc:// deep link. On success, vc-issue-proxy updates Table Storage status to credential_issued.
vc-issue-proxy (Anonymous) vc-issue (Function key) Microsoft Entra Verified ID did:web:www.dgajic.com AI_Governance_Expert credential Azure Table Storage
7
Credential acceptance — Microsoft Authenticator
claim.html displays the QR code with a 5-minute countdown timer. User scans with Microsoft Authenticator (or taps the deep link on iPhone native mail). Authenticator fetches the credential definition from the manifest URL, presents the AI Governance & Cybersecurity Specialist card to the user, and on acceptance stores it cryptographically signed in the wallet. If the QR expires, "Generate new QR code" calls vc-issue-proxy again — allowed within the 15-minute window.
Microsoft Authenticator W3C Verifiable Credential openid-vc:// protocol
8
Credential presentation — vc-present
Any relying party can verify the credential at index.html. vc-present calls Microsoft's createPresentationRequest API, generates a verification QR code. User scans with Authenticator and taps Share. The relying party receives a cryptographic proof — name, email, issuer DID — without storing any copy of the original data. The credential's digital signature is verified against did:web:www.dgajic.com.
vc-present Microsoft Entra Verified ID did:web:www.dgajic.com Zero-knowledge proof of identity

Key Design Decisions

Three decisions worth discussing

These are the architectural choices that had the most impact on security, user experience, and reliability.

Security Pattern
Proxy function to hide the issuance key from the browser
The problem: vc-issue requires a function key to prevent unauthorized credential generation. But claim.html runs in the browser — any key placed in JavaScript source is publicly visible in Developer Tools.

The solution: vc-issue-proxy is an Anonymous function that sits between the browser and vc-issue. The browser calls the proxy with no key. The proxy validates input, applies the single-use gate, and calls vc-issue internally using the key stored in Azure environment variables — which are never transmitted over any public network. CORS is restricted to https://www.dgajic.com to prevent the proxy itself from being called from unauthorized origins.

The pattern: Public-facing anonymous proxy → validated call to protected internal resource. Standard API gateway pattern applied at the function level.
UX vs. Security
On-demand QR generation instead of emailing a static QR code
The problem: Microsoft Entra Verified ID QR codes expire in 5 minutes. Early versions of the pipeline emailed the QR code as an image — by the time the user opened the email, the code had expired.

The solution: The credential email contains only a permanent HTTPS link to claim.html. When the user clicks it, the page calls vc-issue-proxy at that moment, generating a fresh QR code. A 5-minute countdown timer is displayed. If it expires, "Generate new QR code" generates another immediately — allowed within a 15-minute window after first issuance, then blocked to prevent duplicate credential generation.

The benefit: Works in all email clients (Gmail, Outlook, iOS Mail) because HTTPS links are never blocked. The deep link button in the browser (not in the email) works correctly in Safari and Chrome on iPhone.
Reliability
Dual webhook parsing for Veriff test vs. live payload formats
The problem: Veriff's test-mode webhook and live fullauto webhook have different JSON structures. The test format nests data differently from the production fullauto format — a fact not prominently documented.

The solution: vc-onboard checks body?.eventType === 'fullauto' first to identify which format arrived, then uses the matching extraction path for each field. A single boolean flag (isFullAuto) is set once at the top of the function and reused across all field extractions — clean, readable, and easy to extend if Veriff adds more formats.

The lesson: Don't trust API documentation alone — test in production conditions. The bug was only discovered when the first live Veriff verification arrived and the webhook silently produced undefined for all fields.
