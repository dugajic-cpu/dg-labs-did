Architecture Technique

Pipeline d'onboarding KYC par identité vérifiable

Un pipeline serverless de niveau production combinant vérification OTP par email, vérification biométrique de passeport, émission de credential Microsoft Entra Verified ID et présentation cryptographique. Construit sur Azure, déployé et testé avec de vrais utilisateurs externes.

Flux du pipeline

Neuf étapes de l'email au credential vérifié

Chaque étape est une fonction serverless discrète. Le pipeline est event-driven — aucun composant ne tourne ni ne coûte entre les invocations.

1
Vérification email — OTP
Le demandeur visite onboard.html, entre son email et complète le reCAPTCHA v2. send-otp valide le reCAPTCHA côté serveur avec l'API Google, applique une limite de débit de 3 requêtes par 10 minutes par email, génère un OTP à 6 chiffres, le stocke dans Azure Table Storage avec une expiration de 10 minutes, et l'envoie via Microsoft Graph API. verify-otp vérifie le code et le supprime en cas de succès — empêchant les attaques par rejeu.
send-otp verify-otp Azure Table Storage Microsoft Graph API Google reCAPTCHA v2
2
Soumission de demande & enrichissement
Après vérification OTP, le demandeur soumet son nom et son pays de passeport. submit-request extrait l'adresse IP depuis les en-têtes x-forwarded-for, analyse le navigateur/OS/type d'appareil depuis la chaîne user-agent, appelle ipwho.is pour l'enrichissement géographique (ville, région, FAI, fuseau horaire), et stocke tous les champs dans Table Storage. Envoie un email de notification admin avec le contexte complet via Microsoft Graph.
submit-request Azure Table Storage Microsoft Graph API ipwho.is (API géolocalisation)
3
Revue & approbation administrateur
L'administrateur se connecte à admin.html protégé par Microsoft Entra MFA. Après login Microsoft, une validation de clé de fonction assure une deuxième couche d'authentification. Le panneau admin affiche toutes les demandes avec IP, géolocalisation et données d'appareil. Sur approbation, approve-request crée une session de vérification Veriff avec l'email du demandeur dans vendorData, envoie le lien Veriff par email, et met à jour le statut dans Table Storage à veriff_sent.
approve-request list-requests Azure Static Web Apps (auth) Microsoft Entra ID MFA API Veriff Azure Table Storage
4
Vérification biométrique — Veriff
Le demandeur reçoit le lien Veriff par email (valide 7 jours) et complète la vérification passeport + selfie sur son téléphone. Le moteur Full Auto IA de Veriff évalue la soumission — généralement en quelques secondes. Aucune revue humaine requise. L'email est stocké dans vendorData pour relier la session Veriff à l'enregistrement DG Labs.
Veriff Essential — Full Auto IA Biométrique passeport + vivacité Niveau d'assurance aligné FINMA
5
Webhook Veriff — vc-onboard
Sur approbation, Veriff déclenche un webhook fullauto POST vers vc-onboard. La fonction analyse le payload (gérant les formats test et live fullauto), extrait l'email du demandeur depuis vendorData, et construit une URL claim.html personnalisée contenant email, prénom et nom en paramètres URL. Envoie l'email "Votre credential est prêt" avec un lien de réclamation permanent via Microsoft Graph.
vc-onboard Webhook fullauto Veriff Microsoft Graph API
6
Émission de credential — proxy + Entra Verified ID
Le demandeur clique sur le lien de réclamation, qui ouvre claim.html et appelle immédiatement vc-issue-proxy. Le proxy valide les entrées, vérifie Table Storage — si le statut est credential_issued et que plus de 15 minutes se sont écoulées, il retourne 403 (bloqué). Sinon il appelle vc-issue en interne avec la clé de fonction stockée dans les variables d'environnement Azure (jamais exposée au navigateur). vc-issue s'authentifie avec l'API Verified ID de Microsoft via client credentials flow, construit la demande d'émission avec authority, manifest, type et claims, et retourne un QR code (PNG base64) et un deep link openid-vc://. En cas de succès, vc-issue-proxy met à jour le statut à credential_issued.
vc-issue-proxy (Anonyme) vc-issue (Clé de fonction) Microsoft Entra Verified ID did:web:www.dgajic.com Credential AI_Governance_Expert Azure Table Storage
7
Acceptation du credential — Microsoft Authenticator
claim.html affiche le QR code avec un compte à rebours de 5 minutes. L'utilisateur scanne avec Microsoft Authenticator (ou tape le deep link sur iPhone). Authenticator récupère la définition du credential depuis l'URL du manifest, présente la carte AI Governance & Cybersecurity Specialist à l'utilisateur, et sur acceptation la stocke signée cryptographiquement dans le wallet. Si le QR expire, "Générer un nouveau QR" en génère un autre immédiatement — autorisé dans les 15 minutes après la première émission, puis bloqué.
Microsoft Authenticator W3C Verifiable Credential Protocole openid-vc://
8
Présentation du credential — vc-present
Toute partie de confiance peut vérifier le credential sur index.html. vc-present appelle l'API createPresentationRequest de Microsoft, génère un QR de vérification. L'utilisateur scanne avec Authenticator et tape Partager. La partie de confiance reçoit une preuve cryptographique — nom, email, DID émetteur — sans stocker aucune copie des données originales. La signature numérique du credential est vérifiée contre did:web:www.dgajic.com.
vc-present Microsoft Entra Verified ID did:web:www.dgajic.com Preuve cryptographique d'identité

Décisions Clés de Conception

Trois décisions à discuter

Ces choix architecturaux ont eu le plus grand impact sur la sécurité, l'expérience utilisateur et la fiabilité.

Pattern Sécurité
Fonction proxy pour cacher la clé d'émission au navigateur
Le problème : vc-issue requiert une clé de fonction pour empêcher la génération non autorisée de credentials. Mais claim.html tourne dans le navigateur — toute clé placée dans le JavaScript source est visible dans les outils de développement.

La solution : vc-issue-proxy est une fonction Anonyme qui s'interpose entre le navigateur et vc-issue. Le navigateur appelle le proxy sans clé. Le proxy valide les entrées, applique la porte à usage unique, et appelle vc-issue en interne avec la clé stockée dans les variables d'environnement Azure — qui ne sont jamais transmises sur un réseau public. Le CORS est restreint à https://www.dgajic.com.

Le pattern : Proxy public anonyme → appel validé vers ressource interne protégée. Pattern API gateway standard appliqué au niveau fonction.
UX vs. Sécurité
Génération QR à la demande plutôt qu'email d'un QR statique
Le problème : Les QR codes Microsoft Entra Verified ID expirent en 5 minutes. Les versions initiales du pipeline envoyaient le QR code par email — au moment où l'utilisateur ouvrait l'email, le code avait expiré.

La solution : L'email contient uniquement un lien HTTPS permanent vers claim.html. Quand l'utilisateur clique, la page appelle vc-issue-proxy à ce moment, générant un QR frais. Un compte à rebours de 5 minutes s'affiche. S'il expire, "Générer un nouveau QR" en génère un autre immédiatement — autorisé dans les 15 minutes après la première émission, puis bloqué.

L'avantage : Fonctionne dans tous les clients email (Gmail, Outlook, Mail iOS) car les liens HTTPS ne sont jamais bloqués.
Fiabilité
Parsing dual du webhook Veriff — formats test vs. live
Le problème : Le webhook Veriff en mode test et le webhook live fullauto ont des structures JSON différentes. Le format test imbrique les données différemment du format fullauto de production — un fait peu documenté.

La solution : vc-onboard vérifie body?.eventType === 'fullauto' pour identifier le format reçu, puis utilise le chemin d'extraction correspondant. Un seul flag booléen (isFullAuto) est défini une fois en haut de la fonction et réutilisé sur toutes les extractions de champs.

La leçon : Ne pas faire confiance uniquement à la documentation API — tester en conditions de production. Le bug n'a été découvert que lorsque la première vérification Veriff live est arrivée et que le webhook produisait silencieusement undefined pour tous les champs.
